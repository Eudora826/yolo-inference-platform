## 0. 实测基线

> 桶边界必须基于真实数据。先跑服务打一批请求，把数字填进来。
(预热 → 采集 20 个样本 → 出统计)
> ```powershell 
> curl.exe -s -X POST "http://localhost:8000/predict" -F "file=@cat.jpg" | Out-Null   # 预热
> $t = 1..20 | ForEach-Object { (curl.exe -s -X POST "http://localhost:8000/predict" -F "file=@cat.jpg" | ConvertFrom-Json).inference_time_ms }

### 关键发现 1：图片尺寸几乎不影响推理耗时

cat2.jpg 是 1280×1707，推理 77.93ms，完全落在 cat.jpg 那 20 次的正常区间里。

原因：**YOLO 会把所有输入 letterbox 缩放到固定尺寸再推理**（ultralytics 默认 `imgsz=640`）。模型看到的永远是 640×640，与原图分辨率无关。

对设计的影响：

| | 受图片尺寸影响 |
|---|---|
| 纯推理耗时 | ❌ 基本不受影响 → **分布窄而稳，桶可以切得密** |
| 解码耗时（PIL 解 JPEG） | ✅ 随像素数增长 |
| 上传耗时 | ✅ 随文件大小增长 |

→ **结论：`inference_duration_seconds` 和 `http_request_duration_seconds` 必须用不同的桶。**

### 关键发现 2：客户端测的时间不能用来定桶

`Measure-Command { curl.exe ... }` 测的是整个 curl 进程从启动到退出，混进了 Windows 创建进程的开销（几十毫秒）、curl 初始化、TCP 建连。这些**都不是服务端耗时**。

**要为"指标实际会记录的值"设计桶。** `http_request_duration_seconds` 记的是 `main.py` middleware 里 `REQUEST_LATENCY.observe(duration)` 的那个 `duration` —— 服务端自己测的。所以数据来源应该是：

- **A（推荐）** 终端 A 里 uvicorn 打的 JSON 日志，`duration_ms` 字段
- **B** `curl.exe -s -o NUL -w "%{time_total}"`（curl 内部计时，不含进程启动）

```powershell
$w = 1..10 | ForEach-Object { [double](curl.exe -s -o NUL -w "%{time_total}" -X POST "http://localhost:8000/predict" -F "file=@cat.jpg") * 1000 }
$w | Sort-Object; $w | Measure-Object -Minimum -Maximum -Average
```

### 关于「检测数分布」这一项

现在只有 2 张图，而且**同一张图的检测结果是确定性的**（打 20 次得到同一个数），所以测不出真实分布。

处理方式：先按领域知识估桶（COCO 图片典型 1–20 个目标，服务的 `max_det` 上限 100），在设计文档里注明**这是估计值**，等阶段 04 有了负载生成器（多样图片）再回来校准。**桶边界本来就是可以迭代的。**

### 关于「视频任务总耗时」

**逐个回答这 5 个问题，答案决定上面填什么：**

1. 端到端耗时和纯推理耗时，**为什么要分开测**？只测一个会漏掉什么信息？
2. **检测数量的分布**为什么值得测？（提示：平时每张图 3–5 个目标，某天变成平均 0.2 个，说明什么？）
3. **置信度的分布**为什么值得测？它和上一条在监控什么共同的东西？

5. **类别维度**怎么加？COCO 的 80 个类别名当标签，安全吗？为什么？换成 10000 类的模型呢？

**不该做成指标的**（提醒自己）：
- ❌ 每次检测的框坐标 → 日志/链路的事
- ❌ 每个 request_id 的耗时 → 基数灾难
